# My Portal Workspace — ChatGPT MCP Apps

The authenticated sidebar **道場統括 / スキル道場** is an interactive *training workbench*; the original **Projects / Context** tab remains available. Existing OAuth and the `ui://my-portal/workspace.html` entrypoint remain unchanged.

## Dojo Command Center

The default **道場統括** tab is the on-demand front door. Its unified queue shows up to three cards per page, interleaving trial groups and linked submarine hauls rather than hiding measurement dojos with no trials. The existing reserved read-only `portal_workspace_contexts({projectId:"dojo:__queue"})` returns trial entries, bounded haul previews (up to six candidates per active linked submarine), independent trial/haul counts, canonical action lists, and per-source errors. More candidates are loaded as decisions remove items from the queue; no unrelated outcome approval is converted to a trial.

- Images and links: use the actual trial image URL or haul record thumbnail/image URL, plus safe HTTPS links in the body/ref. Existing origin allowlist and link fallback apply. No external image proxy or guessed thumbnail.
- Unified batch review: trial verdicts use `exploration_trial_rate`, grouped by base ID. Haul actions use `submarine_haul_feedback` per item, with the exact canonical action key, explicit button-based authorization and optional note. The composite key includes record kind, base/ship ID and trial/haul ID. Verify saved trials from fresh detail and haul actions from the returned canonical feedback/readback; a nonterminal action (あとで/検討中/保留) remains a candidate and is not counted as a pass. The UI never applies for jobs, publishes or purchases anything. Ambiguous writes lock the affected card until explicit successful reload; clear the uncertain staged selection instead of silently replaying it.
- Dispatch: `portal_workspace_contexts({projectId:"dojo:__dispatch"})` checks the actual linked active fleet as well as trial and outcome queues, excluding pending trials, five or more candidate hauls on any linked ship, five or more pending confirmations, active sorties and recent open runs. Canonical indexing is reconciled on the existing 15 minute cadence via a lightweight internal status read (no gear bodies); genuinely unavailable ship state blocks its associated dojo. Read fresh ship and dojo gates at selection, skip invalidated candidates, refill to at most three distinct release targets. Stale open runs (at least two hours without an update) may be offered as **resume** candidates, not claimed or taken over by the UI. The agent must independently verify state and follow existing recovery rules.
- Start or save-and-continue requests use `ui/update-model-context` and explicit user-triggered `ui/message`. The model executes in the conversation; the handoff requires a changed sourcing route after unsuccessful research, closing completed or abandoned runs and continuing until a reviewable registered result or a genuine existing stopping condition. No independent subagent, scheduled job or external LLM is created. A message acknowledgement is not proof of completion. Manual context handoff remains available. No automatic retry of uncertain sends.
- Dojo outcome confirmations remain a separate explicit conversation handoff; no new approval authority. The same canonical storage, thresholds and version gates remain unchanged.

## Skill Dojo workbench

- **道場一覧 / 検索 / フィルタ**: all active dojos, those with pending trial/outcome evaluations, and those showing a sustained failure streak. Summary data comes from the established `portal_workspace_open({})` tool, backed by `exploration_base_list({status:"active"})`. Display counts distinguish **見本の評価待ち** (`loop.awaiting`) from **成果の確認待ち** (`outcome.awaitingConfirmation`).
- **進行状況**: method version, currently released skill, number of runs, ratings, pass rate, current/previous skill performance (with sample sizes), outstanding run / warnings, whether research is required before the next sample, previous run and proposed next action.
- **錬成を進める**: choose research/hypothesis verification, evidence-backed sample generation, or failure/calibration analysis. A selection becomes an explicit `ui/update-model-context` handoff; training starts **only after the user submits the message**. When the canonical dojo gate requires research, sample generation is disabled in the selector.
- **見本を評価**: expands up to five pending trial samples from the compact projection of `exploration_base_get({id,view:"brief"})` served by the existing `portal_workspace_contexts({projectId:"dojo:<id>"})`. Shows the real trial body and a source link when safe. The user explicitly clicks 合格 / 惜しい / ボツ, optionally adds a short note, and then **この評価を保存**. This calls the existing `exploration_trial_rate` with the exact trial ID, a verbatim representation of the user's selected verdict/note, and `failStage:"unknown"`. The app then reads back the same compact projection to verify that the trial has left the awaiting queue before showing success or updating stats. A tool error never counts as a rating. If the write may have committed but readback failed, saving that trial is blocked until the user explicitly refreshes, to avoid accidental duplicate feedback.
- **成果の確認待ち**: distinct from trials; it remains a **conversation handoff** so the existing confirmation flow, provenance, and user-approval gates are preserved. Never call `exploration_trial_rate` to confirm an unrelated outcome.
- **仮説・改善**: display current hypothesis candidates and their historical rating counts without treating self-scoring as success. Pick one hypothesis to include its ID in an investigation handoff.
- **手動更新** refreshes the currently selected dojo. Selection state is ephemeral in the iframe. No scheduled job, background agent, or Work Item is created. The command-center start is an explicit conversation message, not a background worker.

## MCP compatibility

The initial Dojo UI called two new app-only tool names, which existing ChatGPT connections cached as unknown. To prevent recurrence, the global app still uses the **registered** `portal_workspace_open` and `portal_workspace_contexts`. The UI requests selected-dojo details through the already-registered `portal_workspace_contexts` tool, using the reserved `dojo:<id>` scope. The server internally calls canonical `exploration_base_get` and returns only a small read-only projection (pending trial bodies, observed ratings, gates, selected hypotheses, next action), avoiding the 50–210 KB full brief in the iframe. Rating invokes the already-existing `exploration_trial_rate` or `submarine_haul_feedback` tools; the latter preserves each submarine's distinct actions. The original project Context behavior is unchanged for normal project IDs. No additional MCP tool name is introduced. `exploration_trial_rate` is an explicit write, invoked only on the user's confirmation in the UI. All data remains in its canonical dojo store.

The inline vanilla JS app uses standard MCP Apps `ui/initialize`, `tools/call`, and `ui/update-model-context`. It does not contact Netlify or Firestore via browser `fetch`, expose secrets, or add build dependencies. Failed detail calls fall back to a list summary with conversation handoff, rather than silently displaying invented records.

## Rules of evidence

All percentages are computed by the canonical server and include their evaluated sample sizes, not invented AI self-assessments. The user selects the verdict. AI may investigate and prepare samples, but may not forge user approval or loosen dojo stopping criteria. Repo branch changes alone do not prove a Netlify deployment or host rendering.
