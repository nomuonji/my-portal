# Meta Strategy — チャット全体を俯瞰する提案ストック

## 目的

特定のプロジェクトの進捗管理やタスクの再配分ではなく、ユーザーとChatGPTの活動全体を一段高い視点から再評価する。事業・学習・個人の制作・行動習慣・技術選定・未知の分野への展開、そして「今やらなくていいこと」まで扱う。

- **入口**: My Portal `/meta`
- **正本**: `metaStrategyProposals`（既存 `documentDb` を使用し、Firestore/Turso両バックエンドに適応）
- **チャット連携**: MCP `meta_proposal_list`, `meta_proposal_get`, `meta_proposal_create`, `meta_proposal_feedback`
- **Web UI**: 認証済み `/api/agent-ideas?resource=meta_proposals` と `meta_proposal_feedback`
- **責務境界**: Agent HQ Work Items / Keywords ideas / Portal Boards / human Thinking Spaces と別の記録

## 提案の品質

1. 事前に `world_map_get`, `meta_proposal_list` と必要な Context / 担当システムの正本を読む。
2. ChatGPT の全会話ログが自動的に読み出せるとは仮定しない。利用できた過去の会話・記憶・Contexts・接続先だけを明示する。最近の発言を過去の優先順位より重視するが、ユーザーが却下済みの案は自動復活させない。
3. 「今すでにやっていることの進捗」ではなく、活動の前提を問い直すこと、分散した課題を抽象化すること、隠れた時間コストや実機会を発見することを優先する。
4. 提案は title / ideaKey / summary / reason / nextStep / category / priority / evidence / uncertainty / context の形で保存する。根拠は日時・実際の参照元・観察内容と、そこからの推論を区別する。アクセスできていないものを観察済みと扱わない。
5. `ideaKey` は同一テーマで安定させる。重複作成時はユーザーの評価、却下理由、採否状態を上書きしない。**提案の採用は実装・配信・公開の包括許可ではない。**
6. 毎回大量に埋める必要はない。新しい価値や観察がなければ追加0件でもよい。件数ではなく提案の精度を追う。ユーザーの見送り理由は次回の発想への負の制約として使用する。

## 継続実行

このリポジトリは単独ではLLMを常駐実行しない。ChatGPT定期タスクの5件枠が満杯の場合、既存の **Agent HQ 共通ディスパッチャー** のスケジューラーに、HQ処理とは分離した軽量な「Meta Strategy scan」を**1日1回だけ追加**して使用可能（既存のManager/Workerの実行契約は変更しない）。単一タスク内の後段として以下を実施する:

- 当日の東京時間15時の起動時のみ実行（残りの09/21時の起動では実施しない）。
- `world_map_get` → `meta_proposal_list` → 必要な最近のユーザー判断/Contexts/Operator観測 → 最大1〜3件 `meta_proposal_create`。
- 失敗したら原因を報告し、ストックできていないものを保存成功と扱わない。いかなるプロジェクト実装も行わない。
- 通知は新しい有望な提案があるときだけ。過去に拒否・見送りとなった同内容を再登録しない。
- 起動時点でMCPの新ツールがまだ現れない場合は無理に既存の「アイデア」「思考テーマ」等へ代替保存せず、未実行として終える。

スケジューラーの実際の設定はこのリポジトリの外部にあり、コードのマージだけで自動実行開始とは言えない。

## UX

主画面では優先度、ステータス、根拠、留保、最初の一手を俯瞰し、採用 / 見送り / 検討中 / 完了 と自由記述理由を保存する。詳細を開かなくても採否を付けられる。レビュー履歴は提案IDと revision で保護する。

今後の改善候補: 完了した提案の追跡結果、テーマ類似の統合、前回のレビュー境界に基づく差分収集。初期実装で巨大なAI自動探索パイプラインを増やさない。
